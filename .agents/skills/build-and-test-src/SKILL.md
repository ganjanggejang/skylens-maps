# React 구현과 브라우저 검증

이 스킬의 목적은 **사람이 테스트하듯 실제 앱을 구동하고, 사용자 동작을 수행해 기능 또는 성능을 검증하는 것**이다. npm run dev로 실행한 앱을 프로젝트에 설치된 **chrome-devtools MCP**로 조작한다. 서버 실행 명령을 제시하거나 코드·빌드·단위 테스트 결과만 확인한 것으로 완료하지 않는다.

구현 시작 전에 이 스킬을 읽고, 앱 구동과 현재 화면 확인 → 작은 구현 → 브라우저 재현 → 수정 → 최종 검증의 흐름으로 작업한다. 기능 작업은 실제 사용자 경로의 기대 결과를 확인하고, 성능 작업은 실제 사용자 시나리오를 실행하며 측정한다.

## 1. 작업 범위와 실행 환경

- 루트 및 변경 경로에 적용되는 AGENTS.md, package.json, 관련 컴포넌트와 테스트를 읽는다. git status/diff로 기존 사용자 변경을 확인한다.
- 요청을 관측 가능한 성공 조건으로 바꾼다. 재현 경로, 입력, 기대 DOM/화면/지도 상태와 영향받는 인접 기능을 정한다. 기능에 맞는 검증만 수행한다.
- MCP 설정은 .codex/config.toml 및 .mcp.config의 chrome-devtools 항목에 있다. 현재 설정은 npx로 최신 서버를 실행하므로 **실제로 노출된 도구 스키마**를 확인한다. 도구 접두사, 인자, 메트릭을 기억에 의존하지 않는다. 설정 변경이나 중복 설치는 하지 않는다.
- 루트 npm 스크립트를 기준으로 실행한다. Windows PowerShell에서는 npm.cmd를 사용한다. 개발 주소는 **http://localhost:3000**, 포트는 strictPort로 고정되어 있다. 기존 서버가 이 프로젝트인지 확인하고 재사용한다. 포트 충돌을 이유로 다른 프로세스를 종료하지 않는다.
- predev/prebuild는 prepare:data를 실행한다. exported_files의 GeoJSON 7개, GeoTIFF 4개와 Styles가 필요하며 public/data에 manifest와 수역 마스크를 만든다. 정확한 파일과 규칙은 scripts/prepare-data.mjs 및 README.md를 읽는다. 데이터가 없거나 잘못되면 원인을 보고하고 가능한 정적 검증을 계속한다. 실제 데이터 검증을 가짜 데이터 성공으로 대체하지 않는다.

### 실제 앱 구동: npm run dev

기존 서버가 없다면 프로젝트 루트에서 다음 명령을 **직접 실행**한다. Windows의 npm.cmd run dev는 npm run dev와 같은 스크립트를 실행한다.

```powershell
npm.cmd run dev
```

1. predev의 데이터 준비와 Vite 준비 로그를 확인하고, 서버가 종료되지 않았는지 확인한다. 장시간 실행은 관리 가능한 세션으로 유지한다. 별도 프로세스로 띄울 경우 숨김 창과 로그를 사용하고 자신이 시작한 PID를 기록한다.
2. MCP로 http://localhost:3000을 열고 앱 화면과 지도 데이터가 실제로 표시될 때까지 관측한다. 서버 준비 로그나 HTTP 응답만으로 앱 구동 성공을 판단하지 않는다.
3. 검증 동안 서버를 유지하고 아래 절차의 클릭·입력·화면 확인과 필요한 성능 측정을 수행한다. 이미 실행 중인 이 프로젝트의 서버를 재사용했다면 그 사실을 기록한다.

실행이 막히면 데이터/의존성/포트/브라우저 연결 중 어떤 단계인지 진단한다. 가능한 구현과 정적 검증은 계속하되, 실제 앱을 조작하지 못한 항목은 **브라우저 검증 미완료**로 보고한다.

## 2. 구현 전 브라우저 기준 상태

1. list_pages로 프로젝트 탭을 찾고 선택하거나 new_page로 연다. 사용자의 다른 탭을 이동하거나 닫지 않는다. 깨끗한 저장소 상태가 필요하면 지원되는 isolatedContext를 사용한다.
2. 대상 URL로 이동한 뒤 take_snapshot을 사용한다. 이 도구는 **접근성 트리**를 제공한다. 실제 DOM 구조, computed style, 위치와 크기는 evaluate_script로 필요한 요소만 읽는다.
3. 실제 UI로 현재 동작 또는 버그를 재현한다. 클릭/입력 전 최신 snapshot의 uid를 사용한다. 탐색이나 재렌더로 요소가 바뀌면 snapshot을 갱신한다.
4. 콘솔의 error/warn/issue와 관련 네트워크 요청을 확인하고 기존 문제를 기록한다. 데이터셋 ID, 언어, viewport, URL, 지도 줌/위치 등 재현 조건을 남긴다. UI/지도 변경은 기준 스크린샷도 확보하고 직접 확인한다.
5. Performance API에서 현재 얻을 수 있는 로딩/리소스 메트릭을 확보한다. 로딩, 지도 렌더링, 검색, 라우팅 또는 반복 작업 성능에 영향을 주는 변경이면 구현 전 동일 시나리오의 trace도 측정한다. 측정할 때 [resources/performance.md](resources/performance.md)를 읽는다.

신규 기능은 기존 진입점과 인접 기능을 기준으로 삼는다. 기존 앱이 실행되지 않으면 원인을 좁히고, 확인하지 못한 기준 상태를 명시한 채 독립적인 구현/정적 검증을 진행한다.

## 3. 구현 중 브라우저 반복 검증

- 기존 React 상태 흐름, MapLibre 레이어/worker, i18n 및 CSS 구조에 맞춰 작은 단위로 변경한다. 브라우저 증거를 원인 분석과 구현 선택에 사용한다.
- 의미 있는 변경 후 HMR 또는 새로고침으로 해당 시나리오를 재실행한다. wait_for의 기대 텍스트나 DOM 상태 등 관측 가능한 준비 조건을 사용한다. 고정 sleep이나 문서 load만으로 지도 데이터/worker가 준비됐다고 판단하지 않는다.
- click, fill, fill_form, press_key, hover, drag 등 현재 제공되는 조작 도구로 사용자 경로를 검증한다. 여러 폼 항목은 fill_form을 우선한다. 입력/상태 변경 뒤 DOM, 화면, 콘솔과 관련 요청을 함께 확인한다.
- evaluate_script는 DOM, computed style, bounding rectangle, Performance API 등 읽기와 진단에 우선 사용한다. React 내부 상태, 비공개 ref, 추정한 window.map을 조작해 성공 상태를 만들지 않는다. 진단용 합성 이벤트/직접 API 호출은 실제 사용자 입력 검증과 구분해 보고한다.
- CSS 문제는 지원되는 get_css_styles 또는 getComputedStyle/레이아웃 측정으로 확인한다. 소스의 CSS 선언과 화면에 실제 적용된 스타일을 구분한다.
- MapLibre의 건물/노선/라벨은 canvas/WebGL에 그려져 snapshot에 나타나지 않을 수 있다. **DOM에 canvas가 있다는 것만으로 지도 검증을 통과시키지 않는다.** 스크린샷의 실제 렌더링, 도구로 가능한 지도 조작, 검색 결과 선택 및 상세 패널/레이어 상태를 함께 확인한다. 기존 공개 진단 API가 있으면 보조 증거로 사용할 수 있다. 도구로 정확한 좌표/제스처를 재현할 수 없다면 그 범위를 미검증으로 남긴다.

## 4. 최종 기능·오류 검증

변경 범위에 맞는 시나리오를 실행하고 기대 결과를 실제 관측값과 비교한다.

| 변경 영역 | 확인할 동작과 증거 |
| --- | --- |
| UI/CSS | 스크린샷, 겹침/잘림/불필요한 스크롤, 읽기 순서와 조작 가능성. 일반 데스크톱과 좁은 viewport 및 변경한 breakpoint 주변. |
| 입력/검색 | 정상 입력, 빈 값/결과 없음, 키보드 선택과 Escape, 빠른 연속 입력 후 최신 결과, 선택 후 지도/패널 반영. |
| 지도/레이어 | 실제 지도 표시, 확대/축소, 토글 후 표시 변화, 선택/해제, 라벨과 하이라이트, 인접 레이어 회귀. |
| 길찾기/비동기 | 출발/도착 선택·교환·초기화, 결과/경로 없음, 처리 중 UI, 연속 요청 후 오래된 결과가 최신 결과를 덮지 않는지. |
| 언어/저장 상태 | 한국어·영어의 변경 문구와 레이아웃, 필요한 경우 새로고침 후 선택 유지. |
| 데이터/오류 처리 | 응답 상태와 내용, 오류 안내/복구. 느린 네트워크나 Offline 재현은 관련 변경에서만 수행하고 설정 복원. |

- 최소한 변경한 사용자 경로, 관련 인접 기능, 새로고침 후 같은 경로를 확인한다. HMR로만 성공한 상태를 최종 결과로 삼지 않는다.
- 최종 탐색 이후 콘솔과 네트워크를 다시 수집한다. 필요하면 preserved 옵션으로 이전 탐색도 확인하되 기준 상태/이전 실행과 섞지 않는다. 페이지네이션으로 관련 기록이 누락되지 않게 한다.
- 콘솔 오류는 get_console_message로 상세/스택을 확인한다. React 렌더링·effect·key 경고, 미처리 예외, worker/WebGL 실패 등을 변경과 연결해 진단한다.
- 네트워크 실패는 get_network_request로 URL, 상태, 응답과 제공되는 진단 정보를 확인한다. manifest, GeoJSON, 수역 이미지, JS worker 등 관련 리소스의 실제 로드를 확인한다. HTTP 200이어도 HTML fallback을 데이터/JS 성공으로 취급하지 않는다. 정상 취소/304와 실제 실패를 구분한다.
- 이번 변경의 오류/회귀는 수정하고 해당 경로를 재검증한다. 기존 오류는 근거와 영향을 남긴다. 콘솔을 지우거나 오류를 숨겨 통과시키지 않는다.

## 5. 자동 검사와 성능 검증

최종 소스 상태에서 루트의 다음 명령을 실행하고 종료 코드와 결과를 확인한다.

```powershell
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run test
npm.cmd run build
```

- 기존 테스트를 활용하고 변경 로직의 회귀 위험에 맞게 검증한다. 단순 스타일/문구 변경에 구현을 그대로 따라 하는 테스트를 추가하지 않는다.
- build의 데이터 준비 실패와 코드 컴파일 실패를 구분한다. 데이터 준비만 막혔다면 npm.cmd run build:app으로 mod 모드 번들 빌드를 추가 확인할 수 있지만, 실패한 build나 브라우저 데이터 검증을 통과로 바꿔 쓰지 않는다. 두 빌드는 같은 dist를 덮어쓰므로 결과의 모드를 기록한다.
- 최종 브라우저에서 기준 상태와 같은 조건의 로딩/리소스 메트릭을 비교한다. 성능 관련 변경은 해당 사용자 동작의 trace와 insight까지 확인하고, 차이가 크거나 불안정하면 동일 조건으로 재측정한다. 조건, 전/후 값, 얻지 못한 지표를 보고한다.
- 개발 환경의 StrictMode, HMR, 소스 변환 비용을 포함한 측정은 개발 환경의 비교로 표시한다. 성능 개선을 주장하거나 배포 전 검증이 요청됐으면 실행 가능한 배포 빌드 환경에서도 확인한다.
- **비개발 모드는 session.json 및 snapshots/<id>/ 데이터를 요구한다**(src/MapView.tsx). npm.cmd run preview만 실행하면 이 계약이 충족되지 않는다. 실제 게임 서버 또는 계약을 충족하는 명시적인 로컬 테스트 환경이 있어야 기능/성능 검증이 가능하다. fixture 결과는 실제 게임 연동 검증과 구분한다. 자동으로 게임 실행·모드 설치·배포를 수행하지 않는다.
- /mod 구현도 변경했거나 최종 게임 모드 패키징이 요청됐다면 루트 AGENTS.md의 build-and-test-mod 지침을 함께 적용한다. /src만 수정한 일반 작업에서는 게임 배포 절차를 추가하지 않는다.

## 6. 완료와 증거 전달

실제 앱에서 사용자 경로를 수행해 성공 조건이 관측으로 확인되고, 관련 자동 검사가 완료되고, 새 오류/회귀가 해결됐는지 확인한다. 성능 작업은 해당 경로의 실제 측정 결과도 있어야 한다. 막힌 항목은 통과 처리하지 않고 검증 범위와 원인을 보고한다.

최종 답변에는 변경 내용, 앱 실행 주소와 실행/재사용 여부, 자동 검사 결과, 실제 브라우저 시나리오의 입력·조작·기대 결과·관측 결과, 콘솔·네트워크 결과, 측정한 성능 값과 한계를 짧게 담는다. 필요한 스크린샷/trace는 ignored artifacts/browser/ 아래 저장하고 클릭 가능한 경로를 제공한다. 로그/요청 증거에는 인증값과 개인 데이터를 노출하지 않는다.

throttling/viewport/언어 등 테스트로 바꾼 설정을 복원한다. 작업용 탭과 자신이 시작한 서버만 정리하고, 계속 사용할 서버를 남겼다면 주소와 세션/PID를 전달한다. 임시 계측 코드가 최종 소스에 남지 않았는지 diff를 확인한다.
